# ผลรีวิว Import Export Control Cloud วันที่ 16 ตุลาคม 2026

> This is the original review snapshot. Subsequent implementation and verified release evidence are recorded in [STABILIZATION-2026-10-16.md](STABILIZATION-2026-10-16.md).

โปรเจ็กต์ให้บริการที่ https://control.import-export.cloud/ แล้ว และอ่าน Odoo ผ่าน HTTPS API ได้ แต่ยังไม่มีระบบ deploy ทุกครั้งที่แก้โค้ดโดยอัตโนมัติ การนำขึ้นเว็บครั้งก่อนดำเนินการเป็นครั้ง ๆ ผ่าน SSH และ Docker หลังตรวจสอบ รายงานนี้เป็นผลรีวิวและข้อเสนอ ยังไม่มีการแก้บั๊กหรือ deploy ชุดใหม่จากรอบรีวิวนี้

## ข้อเสนอด้านการใช้งาน

1. ให้แต่ละ Shipment มีรหัสถาวรของตัวเอง แล้วเชื่อม PO/SO, ตู้, B/L/AWB, บิล และไฟล์เอกสาร แทนการใช้เลข PO เป็นตัวแทนทุกอย่าง รองรับหนึ่ง PO แบ่งส่งและหลาย PO รวมเที่ยวได้ชัดขึ้น
2. ทำหน้ารายการงานวันนี้ที่มีผู้รับผิดชอบ กำหนดเสร็จ และสิ่งที่ต้องทำต่อ เช่น เอกสารขาด เรือถึงแล้ว รอคืนตู้ รอใบเสร็จ เป้าหมายคือให้คนเห็นงานที่ต้องลงมือและยืนยันปิดงานได้
3. แยกต้นทุนประมาณการกับต้นทุนจริง เก็บสกุลเงิน อัตรา วันที่อัตรา และบิลอ้างอิงทุกยอด เพื่ออธิบายส่วนต่างได้ ควรแก้ข้อผิดพลาดการแปลง/แจกแจงเงินก่อนเพิ่มรายงานกำไรหรืออนุมัติต้นทุน
4. แสดงที่มาของแต่ละข้อมูลว่าอ่านจาก Odoo, ผู้ใช้กรอก หรือ AI เสนอ พร้อมเวลาปรับปรุงและผู้ตรวจ AI ควรเสนอข้อมูลให้ยืนยันก่อนเปลี่ยนข้อมูลสำคัญตามขอบเขตที่เจ้าของเลือก
5. กำหนดบทบาทจริงก่อนเพิ่มสิทธิ์ เช่น ผู้ดูอย่างเดียว ผู้บันทึก ผู้ตรวจต้นทุน และผู้ดูแล การมีบัญชีรายคนอย่างเดียวไม่ได้เท่ากับมีสิทธิ์แยกบทบาทแล้ว
6. เมื่อมีผู้ใช้พร้อมกันมากขึ้นหรือข้อมูลเริ่มซับซ้อน ค่อยย้ายการจัดเก็บจาก JSON ไปฐานข้อมูลที่รองรับ transaction แต่ต้องแก้ API/หน้าเว็บเรื่อง revision ด้วย การย้ายที่เก็บอย่างเดียวไม่แก้การทับข้อมูลจากหน้าจอเก่า

- ไม่ได้ทดสอบการแก้/ลบข้อมูลจริงบนโดเมน ไม่ได้อัปโหลดเอกสารธุรกิจจริง และไม่ได้ทำ browser E2E ครบทุกหน้าหรือทุกเงื่อนไข จึงควรทดสอบขั้นตอนผู้ใช้กับข้อมูลแยกใน staging ก่อน deploy ชุดแก้

ชุดทำซ้ำอยู่ในโฟลเดอร์ชั่วคราวของเครื่องตอนตรวจ: import-export-audit-storage-auth-20261016.cjs, import-export-odoo-audit-repro-20261016.cjs และ codex-frontend-audit-20261016.cjs เป็นหลักฐานพฤติกรรมปัจจุบัน ไม่ใช่ regression suite ที่ควรผ่านต่อหลังแก้บั๊กโดยไม่ปรับเงื่อนไข

## ลำดับลงมือที่เสนอ

1. ปิดช่องทางเขียนทับทั้งหมด แก้การยืนยันบันทึกและ revision ของ Tracking/Freight พร้อมทดสอบสองผู้ใช้
2. แก้ FX ที่ผูกเอกสารผิดบริษัท การรวมรายละเอียดข้ามบริษัท และการแจกแจงบิล/อัตราหาย
3. แก้ป้ายและข้อจำกัดน้ำหนักของเครื่องโหลดตู้ รวมถึงการเลือก/บันทึกบิลและการโหลดข้อมูลไม่ครบ
4. แก้บัญชีรายคนให้ไม่เปิดทางเข้าเมื่อไม่มีบัญชี แล้วกำหนดผู้ใช้/สิทธิ์ตามงานจริง
5. สำรองข้อมูลครบชุดและทดสอบกู้คืน แยก staging/data และเก็บรุ่นโค้ดก่อนตั้ง deploy อัตโนมัติ
6. เพิ่มความสามารถตามคำตอบเรื่องงานที่ใช้จริง โดยเริ่มจากส่วนที่ลดงานซ้ำหรือป้องกันข้อผิดพลาดได้มากที่สุด
