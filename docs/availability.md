# Automatic recovery

The public service runs on the server independently of developer computers. Docker restarts exited containers. A host timer checks liveness once a minute and recovers only explicitly configured application/proxy containers after three failures, with a five-minute cooldown. Missing containers, certificate failures and upstream Odoo failures require separate attention; the guardian never recreates data or restarts unrelated containers.

Provision a private JSON configuration for `tools/service-guardian.cjs` containing `stateDir`, `appContainer`, `proxyContainer`, `domain` and optional `appPort`. Use a root-owned systemd oneshot service with a 90-second timeout and `SuccessExitStatus=75`, triggered at boot and every 60 seconds. Keep the script, Node runtime and configuration outside mutable releases. `allowLegacyLiveness: true` supports rollback to older images that return a fresh timestamp without the service identifier.

Release and guardian commands share the same `stateDir` and Linux `flock`. Production backup/promotion also creates a bounded maintenance lease. Run deployments through `tools/release-runtime.cjs`, not an ad-hoc Compose stop, so recovery cannot interrupt the frozen backup. An interrupted release directory lock requires inspection before another deployment; the watchdog itself does not retain a stale lock after a crash.

On Windows, run `tools/install-local-service.ps1` from the project. It copies the supervisor into ignored local service storage and registers a current-user task at logon with repeating recovery. If Task Scheduler registration is unavailable, it installs a current-user hidden logon launcher. This is a development service that starts after user logon; it does not provide service before logon. The supervisor owns its child through IPC, handles exits and failed health checks, and never takes over an unrelated listener. Local scheduled mutations and outgoing mail are disabled.

`/api/alive` reports process liveness. Authenticated `/api/ready` reports Odoo freshness, safe error codes and configured key-expiry metadata. The session bar distinguishes saved data from fresh Odoo data and warns within seven days of key expiry. Set `ODOO_API_KEY_EXPIRES_AT` to the actual ISO timestamp when rotating the private key. This metadata does not extend the credential's validity. Odoo authentication must pass before promoting a release.

Tests cover child/supervisor crashes, hangs, duplicate supervisors, unrelated listeners, truncated responses, restart thresholds/cooldowns, maintenance exclusion, Linux cross-process locks and browser status messages. A single server still cannot serve traffic during its own power/network/provider outage; independent monitoring and a second host are separate availability measures.
