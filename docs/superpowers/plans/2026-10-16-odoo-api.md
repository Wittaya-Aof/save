# Odoo API implementation plan

> For agentic workers: use superpowers:subagent-driven-development. Work only on assigned files; preserve all pre-existing uncommitted changes.

**Goal:** Serve the existing cloud application using fresh Odoo API data and perform the authorized cutover after validation.

**Architecture:** A read-only JSON-RPC client feeds board and supporting-data adapters. The server selects the adapters only for ODOO_DATA_SOURCE=api and retains existing payloads and labelled snapshot fallback.

**Tech Stack:** Existing Node CommonJS, built-in fetch, node:assert and the existing Docker/Traefik deployment; no new dependencies.

**Spec:** docs/superpowers/specs/2026-10-16-odoo-api-design.md

## Review focus

- Company record rules and optional fields must not silently hide required data.
- Pagination, ties and row caps must not silently omit rows.
- Many2one false values and category ties must preserve SQL filter semantics.
- Date cutoffs, credit notes and FX correction must match direct data.
- API errors or cached/snapshot data must not be presented as a fresh successful read.

### Task 1: Read-only client and board adapter

Files: lib/odoo-api.cjs, lib/odoo-boards.cjs, tests/odoo-api.cjs, tests/odoo-boards.cjs.

Interfaces: createOdooClient(env, {fetchImpl,timeoutMs}={}) returns authenticate(), execute(model,method,args,kwargs), searchRead(model,domain,fields,options), searchAll(model,domain,fields,options), searchCount(model,domain), read(model,ids,fields). searchAll paginates deterministically and rejects overflow. createOdooBoards(client,{now}={}) returns boards(board), poLines(board,poNumber), preserving existing raw SQL shapes. The client enforces read-method allowlisting, HTTPS, deadlines and company context; no secret-bearing errors.
